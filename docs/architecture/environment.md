# Environment configuration

One place that explains every environment variable of the system: who reads it, what it defaults to, and how development, test
and container configuration differ. The values and comments in [`.env.example`](../../.env.example) are the template;
`pnpm setup:env` turns it into your git-ignored `.env` with random local passwords.

## Rules

1. **Applications read the environment only through their validated config**: `apps/api/src/modules/config`,
   `apps/worker/src/config.ts`, `apps/web/src/shared/config/env.ts`. A missing or invalid value stops the process at startup
   with a message that **names the variable and never prints its value**.
2. **Secrets are never committed.** `.env` is git-ignored; `.env.example` holds `change-me-*` placeholders only; images contain no
   `.env`; logs never contain credentials (connection URLs are redacted to `scheme://host:port`).
3. **No silent drift.** `pnpm check:architecture` runs `tools/check-env.mjs`, which fails when: an app reads a variable that
   `.env.example` does not document; Compose references an undocumented variable or defaults to a value that contradicts
   `.env.example`; a container receives a variable its app does not read (a typo would be silently ignored) or lacks a required
   one; the worker is given database credentials; `DATABASE_URL`/`REDIS_URL` disagree with `POSTGRES_*`/`REDIS_*`; a real-looking
   password sits in `.env.example`; the worker's Docker stop timeout does not exceed its shutdown grace period; the Dockerfile's
   pnpm/Node versions differ from the repository's.

`AGENTOS_NETWORK`, `AGENTOS_IMAGE_TAG` and `GIT_REVISION` are set by scripts and the system-test harness (network name, image tag, the
commit an image is labelled with), not by developers; their defaults (`agentos-net`, `local`, `unknown`) are right for normal use,
and `check-env` deliberately does not require them in `.env.example`.

`API_PORT` and `WEB_PORT` mean "where you reach it on the host" in both modes, so changing them works the same with `pnpm dev`
and `pnpm stack:up`.

## Development, test and container configuration are separate

| Context           | Configuration source                                                                                                | Data it touches                                                                                                                                                                                                                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm dev`        | `.env` (loaded by the app scripts)                                                                                  | Your dev PostgreSQL/Redis                                                                                                                                                                                                                                                                                 |
| `pnpm stack:up`   | `.env` via Compose interpolation                                                                                    | Your dev volumes (kept across `down`)                                                                                                                                                                                                                                                                     |
| Unit tests        | Set in each vitest config; no infrastructure                                                                        | None                                                                                                                                                                                                                                                                                                      |
| Integration tests | `.env` / CI environment; `NODE_ENV=test`, `LOG_LEVEL=silent`                                                        | Redis **logical database 15** with a unique key prefix per test, deleted afterwards; PostgreSQL tests create and drop a **throwaway database** (`createIsolatedDatabase`, created with `DATABASE_ADMIN_URL`, owned by the migration role, application code connecting as the API role), never the dev one |
| System tests      | **Generated per run**: random passwords and ports in a temp env file; unique Compose project `agentos-systest-<id>` | Their own volumes and network, deleted when the file ends. The harness refuses to delete volumes of any project that does not carry that prefix                                                                                                                                                           |
| CI                | `pnpm setup:env` generates throwaway credentials, **masked in the job log**                                         | A fresh PostgreSQL/Redis created for the run                                                                                                                                                                                                                                                              |

## Database credentials: three roles

| Role              | Used by                                                | Can                                                                                                      |
| ----------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `agentos` (super) | PostgreSQL bootstrap, the `db-roles` job, test tooling | Everything. Never used by the API or the migration process                                               |
| `agentos_migrate` | `pnpm db:*`, the `migrate` service                     | Owns the schemas and tables and changes them. Not a superuser (`CREATEDB` for `prisma migrate dev` only) |
| `agentos_api`     | The API (`DATABASE_URL`)                               | Only what each migration granted to the group role `agentos_app`. Owns nothing, creates nothing          |

`pnpm setup:env` adds the variables of a newer version to an **existing** `.env` without changing any value you already have (and
switches a legacy `DATABASE_URL` that logs in as the superuser to the API role, keeping your host, port and database). `pnpm infra:up`
then provisions the roles on your existing data volume (`infrastructure/postgres/roles.sql`, idempotent, touches no data). See
[docker-compose.md](docker-compose.md#database-roles).

## Registration is closed: how to add a user

The first user of an empty instance can always register (`POST /api/v1/auth/register`); the first organization is created afterwards
through the organizations API (a later step). After that, registration is closed. There are **no invitations yet**, so to let another
person join an operator must set `AUTH_ALLOW_REGISTRATION=true`, restart the API, let that person register, and set it back to
`false`. **While it is `true`, anyone who can reach the API can create an account**: enable it only on a trusted network and only
for as long as needed.

## Production requirements for authentication

The Compose stack is a development and verification environment. A deployment that exposes AgentOS to real users must meet **all** of
these; each is either enforced by the API at startup (marked **enforced**) or an operational requirement nothing in the code can check
for you.

| Requirement                                                                                                                                                                                                                     | Why                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WEB_ORIGIN` **must be an `https://` origin** (exactly the origin browsers use, no path).                                                                                                                                       | It decides the cookie's `Secure` flag and the `__Host-` cookie prefix, and is the only origin a cookie-authenticated state change may come from. With plain `http` the session cookie travels in clear. The API refuses plain `http` away from localhost (**enforced**).                                                                                                         |
| `AUTH_ALLOW_INSECURE_ORIGIN` **must stay disabled** (unset or `false`).                                                                                                                                                         | It exists only so a developer can use an `http://` origin on another host. **Enforced:** with `NODE_ENV=production` the API refuses to start if it is `true`.                                                                                                                                                                                                                    |
| `TRUST_PROXY_HOPS` **must equal the number of trusted reverse proxies** between the client and the API (0 when clients connect to the API directly).                                                                            | The client address, which per-address rate limiting uses, is taken from `X-Forwarded-For` only this many hops deep. Too low: every client looks like the proxy and shares one budget. Too high: a client can pick its own address.                                                                                                                                               |
| **A non-zero `TRUST_PROXY_HOPS` is only safe when untrusted clients cannot reach the API directly.** The proxy must also _overwrite_ the client's `X-Forwarded-For` (as the Compose nginx does), not append to it.              | A hop count cannot tell a proxy from a client. If the API is reachable directly, any client can send `X-Forwarded-For` and choose its address, which bypasses every per-address limit (sign-in, registration). Verified by a test; see below.                                                                                                                                    |
| **The API must not expose a direct or public route that bypasses the reverse proxy.** In production **do not publish the API port**; let only the proxy reach it (private network, security group, network policy).             | The same reason, plus the proxy is where TLS ends. The Compose stack publishes `127.0.0.1:${API_PORT}` for developers only.                                                                                                                                                                                                                                                      |
| **Registration stays closed** (`AUTH_ALLOW_REGISTRATION=false`) unless a controlled onboarding procedure needs it, and then only for as long as needed.                                                                         | While it is `true`, anyone who can reach the API can create an account. There are no invitations yet. Changing it needs an API restart.                                                                                                                                                                                                                                          |
| **Database roles keep the API/migration separation** (see "Database credentials: three roles"): the API connects as a non-superuser that owns nothing; migrations run as a different role; the superuser is not used by either. | The audit trail's append-only protection holds against application code only while the application is not a superuser or the table owner. Both can disable the triggers.                                                                                                                                                                                                         |
| **Redis must be available for sign-in, registration and password change.** Run it with the same care as PostgreSQL for these paths.                                                                                             | They count attempts in Redis and **fail closed** (`503`) when it is unavailable. Existing sessions, `/me` and logout do not need Redis.                                                                                                                                                                                                                                          |
| **Size memory for password hashing**: each API process may hash two passwords at once, **256 MiB** in total (2 x 128 MiB scrypt), on top of its normal footprint.                                                               | The limit of two is **per process, not global**. With `R` API replicas the worst case is `2 x R` simultaneous hashes and about `R x 256 MiB` of transient memory. A container memory limit must cover the Node baseline plus 256 MiB; capacity planning multiplies by the replica count. The cost is never reduced to save memory: requests queue and then answer `503` instead. |

**Checking `TRUST_PROXY_HOPS` against a direct client.** `test/identity.int.spec.ts` and the review probe showed it directly: with
`TRUST_PROXY_HOPS=1`, nine registrations from one socket with nine different `X-Forwarded-For` values all succeeded although the limit
is five per hour per address; with `0` the header is ignored and the limit applies. Only the per-address budgets are affected: the
per-account sign-in budget and the two-hashes-per-process cap are not. An explicit trusted-proxy list instead of a hop count is a
possible later hardening and is **not** implemented.

**Known limitations of authentication rate limiting** (accepted, not solved; also recorded in ADR-0010):

- **Per-account lockout can deny a legitimate user.** Ten failed sign-ins for an account within 15 minutes block that account for the
  rest of the window, whoever made the attempts. Anyone who knows an email address can therefore lock its owner out temporarily.
- **IPv6 address rotation bypasses per-address limits.** The address is used as given, so a client with a whole IPv6 prefix can use a new
  address per request.
- **A missing client address shares one bucket.** If `req.ip` is ever empty, those requests are all counted against the single key
  `unknown`. Express always sets it for a real connection, so this is an edge case, but it is not handled specially.

## Changing configuration safely

- Add a variable: add it to the app's schema, to `.env.example` (documented), and to Compose if containers need it; `check-env`
  tells you what you forgot. Give it a default only if a wrong default is harmless.
- Rotating a database password after the volume exists requires changing it inside PostgreSQL as well (see
  [infrastructure.md](infrastructure.md)); the `.env` value alone only applies to a new data directory.
